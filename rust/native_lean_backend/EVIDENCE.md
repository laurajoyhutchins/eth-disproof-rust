# G1 independent evidence and release ledger

This document tracks checklist [#193, items 31–40](https://github.com/laurajoyhutchins/eth-disproof-rust/issues/193) for the **in-process Lean 4.34.1 → Rust executable-IR compiler**. It does not claim completion of the general-purpose compiler (G1) or of the source-defined ETH program (G2).

## Reproduce at a checked-out, exact revision

Prerequisites: Linux x86-64; the exact Lean 4.34.1 compiler/headers at commit `5045d0056413266e57c625dcd7c365b10e377c52`; Rust/Cargo 1.99.1; a C compiler; `ar`; and the existing pinned dependency/ABI checks in `build.rs`.

```sh
cd rust/native_lean_backend
export LEAN_PREFIX=/absolute/path/to/pinned/lean-4.34.1
lake build
bash scripts/check.sh
bash scripts/check-evidence.sh
# Optional performance observation, NOT a backend speedup comparison:
bash scripts/bench-evidence.sh
# Three-way executable runtime parity and high-resolution measurements:
bash scripts/check-native-runtime-parity.sh
```

The normal public API remains `#native_rust Name as "export" to "file.rs"` (single executable declaration) and `#native_rust_closure Name as "export" to "file.rs"` (direct-call closure through imported executable IR). Both require loading the built native shared library into the same Lean process with `--load-dynlib`. `scripts/check.sh` provides the reproducible invocation and configures environment paths. This is **not yet** a one-command general-purpose installation or a multi-root Cargo emitter; see #193 G1-A.

### Deterministic property differential suite

`examples/PropertyDef.lean` defines a bounded-depth, scalar recurrence with unsigned wrapping, conditional branches, and recursive calls. It is compiled as an ordinary imported Lean declaration. `examples/Property.lean` directs the native compiler to emit the standalone Rust implementation and **independently asks Lean to evaluate** the original declaration for 128 fixed seeds and eight deterministic shrink candidates per seed.

`examples/property_driver.rs` runs the generated Rust against all 1,024 Lean-produced outputs. On mismatch, it prints the seed, input, fuel, original Lean output, generated Rust output, shrink stage, and a one-seed reproduction command; it chooses the smallest failing candidate in the precomputed ladder. This is **bounded, precomputed shrinkage**, not a claim of globally minimal counterexamples or of full QuickCheck-style generation.

The test seed sequence is generated by a fixed-width 64-bit LCG starting at `0x9E3779B97F4A7C15`. Boundary inputs include 0, 1, 2, 3, 7, 42, `2^32-1`, `2^32`, `2^63`, `2^64-1`. Oracle values are computed by Lean, not copied from or reconstructed by the Rust backend.

The suite also compiles the emitted code as a **new standalone Cargo executable** with no Lean runtime dependency, runs debug and release tests (`cargo test --offline` and `cargo test --release --offline`), enforces `#![forbid(unsafe_code)]`, checks `cargo clippy --offline --all-targets -- -D warnings`, checks dynamic links with `ldd`, and runs the optimized executable. The existing `scripts/check.sh` separately exercises ABI, 1,984 fixed/seeded Lean/Rust assertions, refusal preservation, deterministic closure, and backend unit tests. Neither fixture replaces testing on independent Lean projects.

### Performance evidence policy

`scripts/bench-evidence.sh` runs a cheap, bounded three-trial measurement on the same original `Property.hop` declaration. It records **fresh-process**, cache-uncontrolled measurements in `artifacts/bench-native/measurements.tsv`, with source/toolchain identities and raw logs:

- In-process Lean→Rust codegen using precompiled `PropertyDef.olean` and `PropertyCodegen.lean`; the independent oracle is **excluded** from these timings.
- Lean's original pinned `lean -c` backend generating C from `PropertyDef.lean`, then `cc -O2` compiling that source to a native object.
- Generated Rust `rustc -O` build, generated executable runtime, wall time, peak RSS, emitted source/object/binary bytes and deterministic output hashes.

These are **not apples-to-apples end-to-end comparisons**. The Lean C invocation re-elaborates source, while the Rust FFI path imports existing compiled IR; the C result is an object, not a matching executable with measured runtime, and the older JSON/source-graph path does not yet support this exact `UInt64` program. No C-vs-Rust or JSON-vs-Rust speedup is claimed, and the three runs do not measure cold OS caches. The full equivalence and measurement requirement in item 36 therefore remains open.

For #193 item 36, extend this harness only after constructing a **shared supported program with identical inputs, outputs, and algorithm** across all three backends. Then measure source hash, toolchain, cold/warm definitions, process startup, compilation, intermediate bytes, execution, RSS, and refusal rates separately. If any backend cannot compile that common program, record **unsupported**, not an invented runtime comparison.

## Imported standard-library probes (not three external projects)

The exact pinned original Lean 4.34.1 source is exercised without hand-copying or rewriting implementations. `examples/ProbeNatGcd.lean`, `ProbeListReverse.lean`, and `ProbeStringIntercalate.lean` independently check real original Lean behavior, then attempt native in-process extraction. All three **explicitly refuse** unsupported compiled IR in [native CI 43507863090](https://github.com/laurajoyhutchins/eth-disproof-rust/actions/runs/43507863090), commit `714524c06e8ee2b47a74957722abf052f9831e72`. Their original behavior is valid, but generated Rust does **not** exist. Precise refusals, prior-output preservation, and peak RSS/time are saved in `artifacts/imported-probes/`. This provides a reproducible negative coverage baseline. It **does not** satisfy checklist item 32's requirement for three nontrivial independent projects actually building and running.

## Three independent source-pinned Lean projects

`scripts/check-external-projects.sh` performs **sparse, shallow, immutable-commit checkouts** from three independent upstream GitHub repositories. It never changes their source. In each project's own original Lean 4.34.1 Lake workspace, it builds an original substantial module and runs a separate `#guard` against that module's real executable definition. It then attempts direct in-process IR extraction without substituting or rewriting the algorithm. A refused extraction must leave an existing Rust sentinel unchanged. Original source and upstream Git tree SHAs, toolchains, build/oracle/codegen wall/RSS, diagnostic logs, and compiler revision are recorded.

[Exact-head native run 43611081595](https://github.com/laurajoyhutchins/eth-disproof-rust/actions/runs/43611081595), commit `ebc618026592c832d619291decd2e63bb0e71a87`, plus [raw evidence artifact 14120635627](https://github.com/laurajoyhutchins/eth-disproof-rust/actions/runs/43611081595/artifacts/14120635627):

| Repository, pinned commit | Original unchanged module/definition | Original Lake + Lean oracle | In-process Rust extraction | Lake wall / compiler refusal wall |
| --- | --- | --- | --- | --- |
| `newspeaklanguage/newspeak@8e8ed029` | `Newspeak.PEG` / `Newspeak.ConcreteTree.span` (185-line module, parsing semantics) | PASS / PASS | **REFUSED**: object IR type tag 7 | 1.24 s / 0.26 s |
| `AshishKumar4/armada@c12b4a57` | `Sched.Basic` / `Sched.argLeastLoad` (450-line scheduler + proofs) | PASS / PASS | **REFUSED**: a noncanonical `Lean.Name` component | 0.94 s / 0.26 s |

These are **real successful original Lean builds and behavior checks**, but **zero successful extracted Rust programs**. No cross-language semantic comparison for these external roots exists yet. All three refusals correctly preserved prior output. Thus this is a genuine negative coverage matrix, **not item 32 acceptance**. Codegen refusal RSS was around 832–834 MB, including Lean process/module startup, on this runner.

The real-world `Lean.Name` refusal motivates a structured-name adapter (pass the actual `Lean.Name` object over FFI, encode nonstandard string/numeric components injectively), while object IR tag 7 requires exact object layout, allocation and ownership semantics, not a permissive type cast. Neither refusal may be silently changed to a successful result until the emitted Rust compiles, executes, and matches original Lean behavior.

## Atomic bundle publication and build receipts

`scripts/compile-bundle.sh` is a reproducible build wrapper around the existing in-process Lean compiler. It does not replace its backend or introduce serialized JSON IR. A successful invocation accepts an imported module, actual root, source file, new destination directory, and optional Rust export name:

```sh
cd rust/native_lean_backend
# First build the backend using the pinned toolchain and scripts/check.sh.
mkdir -p artifacts/bundles
bash scripts/compile-bundle.sh PropertyDef Property.hop \
  examples/PropertyDef.lean artifacts/bundles/property-hop property_hop
```

The script stages the module's original source, Lean `.olean`, a temporary command, generated Rust source, a strict `rustc -D warnings` standalone Rust library, and `closure.txt` extracted from generated IR declarations. It records the exact source/revision/toolchain, original source SHA-256, compiled module SHA-256, native ABI and backend SHA-256, native plugin SHA-256, declaration-closure hash, generated Rust hash, and emitted library hash in `receipt.txt`, then **publishes the entire directory as one atomic rename**. Existing destinations and invalid roots/output paths refuse. Failed or unsupported compilation leaves no published partial directory. `scripts/check-bundle.sh` verifies both success and negative cases on pinned CI.

A receipt with `status=GENERATED_COMPILED_UNVERIFIED` means **only** that the generated standalone Rust library compiled cleanly. It is not a semantic conformance report. The original module source and generated closure are included, but transitively imported modules are **not yet exhaustively hashed**. Direct use of the low-level `#native_rust`/ `#native_rust_closure` commands does not automatically produce such a bundle; consequently checklist #39 still remains open until this becomes the standard interface and all successful builds carry the specified complete evidence.

### Observed startup/import costs and verified narrowing

Pinned hosted-runner measurements on the same source (`Property.hop`) show a substantial import footprint. The matching `PropertyControl.lean` process loads the same `NativeRust` and `PropertyDef` modules and the same Rust native library **without** invoking the backend. This is a control for startup/imports, not a pure compiler-time measurement.

| Three-trial measurement | Broad `import Lean`, [run 43510095523](https://github.com/laurajoyhutchins/eth-disproof-rust/actions/runs/43510095523) | Narrow module imports, [run 43510481607](https://github.com/laurajoyhutchins/eth-disproof-rust/actions/runs/43510481607) |
| --- | ---: | ---: |
| Import-only control, wall | 0.70–0.72 s | 0.30 s |
| Import-only control, peak RSS | ~1.61 GB | ~0.83 GB |
| In-process codegen, wall | 0.70–0.73 s | 0.33–0.36 s |
| In-process codegen, peak RSS | ~1.61 GB | ~0.83 GB |

Replacing `import Lean` with `Lean.Compiler.Main`, `Lean.Compiler.IR.CompilerM` and `Lean.Elab.Command` reduced the **observed** median in-process wall time from 0.70 s to 0.34 s (about 51%) and peak RSS by about 48%. The compiler also reuses executable IR already present in imported `.olean` modules; the full pinned differential/refusal suite remained green. Since both changes are in the same revision and runners are not identical, **the data does not isolate the causal contribution of each change**. The near-equality between import-only and codegen costs suggests imports/startup account for most measured cost on this example.

The pinned Lean C source-generation control remains around 0.19–0.20 s and ~490 MB on the post-change runner, but no performance superiority/inferiority is claimed across backends. Source elaboration, caching, artifact boundaries, and executable runtime differ. The legacy JSON/source-graph path has no equal supported `UInt64` input here, so the required three-way end-to-end comparison is still **open**.

### Executable runtime parity: original Lean, Lean C, generated Rust

`scripts/check-native-runtime-parity.sh` uses the **original** `Property.hop` declaration from `PropertyDef.lean`. `PropertyNativeBenchmark.lean` is an input-loop adapter, not a rewrite of the function. The script generates native Lean C for the original module and the adapter, links with the pinned Lean 4.34.1 `leanc` wrapper, compiles the in-process-backend's standalone emitted Rust with `rustc -O`, and executes the original Lean source directly as an independent third oracle.

All three paths process **1,048,576 identical deterministic inputs**. The checksum is `1595490202785243536` for original Lean execution, compiled Lean C, and standalone generated Rust, on [exact-head CI 43572940012](https://github.com/laurajoyhutchins/eth-disproof-rust/actions/runs/43572940012), commit `a8fcb62eadc5d3e6656d88aff2e21f4892b33a89`. The [raw artifact 14104703827](https://github.com/laurajoyhutchins/eth-disproof-rust/actions/runs/43572940012/artifacts/14104703827) contains exact source hashes, original generated C and Rust hashes, executable hashes, checksums, 3 peak RSS observations per backend, and 30 independently checksum-validated subprocess elapsed-time samples per backend. All tests in the existing native suite also passed.

| Executable backend | Median subprocess wall, 30 trials | Important distinction |
| --- | ---: | --- |
| Lean 4.34.1 native C | 30.88 ms | Links to and starts the Lean runtime |
| Rust generated from live Lean compiler IR | 7.72 ms | No Lean runtime dependency |

This is an **observed 4.0× subprocess wall-time ratio on one authored supported program**, not a general performance result, pure function throughput, controlled cold/warm comparison, or translation theorem. Process startup, allocator, library loading, cache/frequency effects, and generated code differ. GNU `/usr/bin/time` has only 0.01-second resolution for this workload, so `examples/bench_subprocess.rs` uses `Instant` with 30 alternating-order, checksum-validated subprocess runs and records nanoseconds. This is standard-library-only Rust, with no Python or third-party benchmark framework.

**Still missing for item 36:** a common end-to-end accepted program on the legacy JSON/source-graph path, fair same-phase cold and warm compilation accounting, and independent substantial-project data. For item 37, the in-process path demonstrably avoids serialized JSON IR, but no valid end-to-end speedup relative to the legacy path is established.

### Claim boundary

**Tested, once CI is green:** the pinned Lean compiler object passes in process to the Rust backend, and the supported scalar/Boolean/direct-recursive subset produces matching outputs on the enumerated finite fixtures. Negative refusals and independent emitted-Cargo build are also tested.

**Not proved:** a general semantic-preservation theorem, all reachable Lean IR/runtime semantics, absence of memory errors across arbitrary inputs, full transitive coverage, a standalone ETH program, source-defined noncomputable residualization, physical trace parity, or asymptotic resource bounds. Unreachable/unsupported IR remains a precise refusal obligation, not an implicit host implementation.

## Troubleshooting and refusal policy

- `Expected Lean 4.34.1` or ABI mismatch: install the **source-pinned** release and headers, not a nearby Lean version. Do not bypass `build.rs` checks.
- Missing `LEAN_PREFIX`, shared library, or `NativeRust.olean`: run the documented baseline `check.sh` after `lake build`. Its environment variables are process-local.
- Unsupported primitive, `sorryAx` dependency, missing imported IR, invalid output identifier, or unsupported runtime value: treat the failure as **unsupported source**, not a compiler success. The codegen command must refuse the whole closure and preserve the previous output.
- Property mismatch: run `examples/property-test --seed N`; preserve the emitted Rust, `PropertyDef.lean`, seed/stage and complete receipt before reducing the case.
- Cargo/Clippy failures in generated Rust: this is a compiler defect within the supported subset, not a reason to disable strict validation.
- Out-of-scope data types and noncomputable ETH declarations: do not substitute a rewritten algorithm or an exponential fallback.

The CI receipt is **evidence of a run at a commit**, not a mathematical proof. Mark a G1 item complete only after an accepted source change and a successful exact-head report, or a reviewed documentary-only contract.
